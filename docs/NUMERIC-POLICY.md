# 수치 타입 정책 — 반올림 지점과 포팅 전략 (NUMERIC-POLICY)

> **목적**: TS `number`(IEEE754 double) → Rust 수치 타입 포팅 시 **로그 100% 일치**를 위해
> 반올림/분수 연산을 어떻게 다룰지 결정한다. 반올림 지점 전수 목록은
> [`INVARIANTS.md` Part 5](INVARIANTS.md#part-5--수치-반올림-지점-ulp-함정--포팅-시-정확-복제-대상).
>
> **상태**: 분석·권고(🔸). 실제 포팅은 검증 인프라(1~6단계) 완료 후. 지금은 **반올림 지점을
> 스트레스 런 하네스+self-consistency가 동일성으로 묶어두는 것**이 1차 방어.

---

## 1. 문제

게임 로직에 **분수가 발생하는 단 하나의 본질적 원천**은 포메이션 총량보존이다
(`getFormationBonus = total / count`, 예 `4/3`). 이 분수가 데미지/쉴드/힐 계산에 합산된 뒤
`Math.round`로 정수화된다. 그 외 모든 수치는 정수(스탯·스택·골드·hp)다.

TS는 모든 수를 f64로 다룬다. Rust로 옮길 때:
- **f64 그대로** 쓰면 IEEE754 연산이 비트 단위로 같아야 로그가 일치한다(곱·합 **순서**까지 동일해야).
- **정수/고정소수점**으로 재설계하면 부동소수 의존이 사라져 결정론이 구조적으로 안전해진다.

## 2. 반올림 지점 요약 (Part 5 발췌)

| 분류 | 지점 | 본질 |
|---|---|---|
| **분수 원천** | R6 `formation.ts total/count` | 유일한 비정수 생성. 나머지는 이걸 소비. |
| **최종 정수화** | R1 데미지 `Math.round` · R4/R5 쉴드·힐 `Math.round` · R8 회복비율 `Math.round` | 분수+정수 누적 후 1회 round. |
| **floor 경계** | R2/R3 공포 `floor(shield/mult)` | 정수 shield의 정수 나눗셈 — f64에서도 정확(분수 아님). |
| **부동 누적** | R7 crit 배수 합 | round 직전까지 비정수 부동. 합산 순서 민감. |
| **순정수** | R9 옵션 수 clamp | 안전(목록화만). |

핵심: **분수는 R6 한 곳에서만 생기고, R1/R4/R5/R8에서 정수로 닫힌다.** floor(R2/R3)는 정수/정수라 부동소수 함정이 아니다.

## 3. 정책 옵션

### (A) f64 엄격 일치 — 포팅 시 반올림 지점 정확 복제
- Rust도 f64, `Math.round`(half-away-from-zero, 단 JS는 half-up: `.5→올림`)를 **정확히** 복제.
- 곱·합 **순서 고정**(R7 crit 배수 누적 순서, R1 base 합산 순서)을 코드로 박제.
- 장점: 재설계 0. 단점: f64 반올림 규칙·순서를 영원히 동결해야 함(미세 리팩터도 로그 위협).

### (B) 정수/고정소수점 재설계 — 권장 🔸
- 포메이션 분배를 **정수 몫·나머지 분배**로 재설계: `total/count` 대신 각 유닛에 `floor(total/count)`,
  나머지 `total mod count`를 **결정론적 순서(uid 정렬)**로 +1씩 분배 → 유닛별 정수 보너스, **합=total 정확 보존**(K1 누적오차 동시 해소).
- 모든 데미지/쉴드/힐이 정수 입력만 받게 되어 `Math.round` 자체가 불필요해짐(R1/R4/R5도 정수 연산).
- 장점: 부동소수 의존 제거 → Rust `i32`/`i64`로 자명하게 일치, K1(반올림 후 총량보존) 결함도 해결.
- 단점: 지금 `getFormationBonus` 소비처(damage/skills/status) 시그니처·테스트 골든이 바뀜 → **별도 슬라이스**.

## 3.5 적용 현황 (옵션 B 채택 — 2026-06)

- **슬라이스1**: 포메이션 분배 정수화(몫+나머지 uid 분배, 합==total).
- **P0-2 zero-f64**: crit배수·frost·회복/피해 pct를 **정수 퍼센트(×100)**로(데이터값+공식). 단일 정수 반올림 `roundDiv(n,d)=⌊(n+d/2)/d⌋`(`util.ts`, n≤0→0). R1(crit/frost)·R4/R5·R8 해소. **코어 게임수학 f64 0.** 골든 코퍼스·전 테스트·15000 스트레스에서 **관측 변화 0**(f64와 정수-유리수 반올림이 코퍼스 입력에서 일치 — 이론상 차이는 f64 비정확 .5 경계의 미검증 입력에서만).
- **잔존 f64(의도)**: ① `rng.ts` PRNG `(state>>>0)/2^32`(RNG 프리미티브 — Rust가 u32+부호계약으로 정확 복제, SERIALIZATION-CONTRACT) ② `ai/profile.ts` 점수 `*0.1`(행동 선택용 — 행동벡터 재생 시 Rust는 행동 재생하지 AI 재실행 안 하므로 **differential 무관**, 이연).

## 4. 권고

1. **지금(검증 단계)**: 재설계하지 않는다. 반올림 지점을 **self-consistency harness + 무작위 스트레스 런**이
   "같은 시드 2회 = 동일 로그"로 묶어 **현재 f64 거동을 골든으로 동결**한다. 이게 어떤 재설계든의 안전망.
2. **포팅 직전**: 옵션 **(B) 정수화**를 별도 슬라이스로 수행하는 것을 강력 권고. 포메이션 분배만
   정수 몫·나머지로 바꾸면 분수가 사라지고 K1 결함까지 해소된다. 이때 골든 로그가 의도적으로 바뀌므로
   **재설계 전후를 self-consistency로 각각 고정**하고 변경을 리뷰한다.
3. (B) 채택 전까지는 옵션 **(A)** 가 자동 적용 상태 — 합산 순서를 바꾸는 리팩터는 골든 회귀로 잡힌다.

## 5. 체크리스트 (포팅 슬라이스에서)

- [ ] R1/R4/R5/R8의 `Math.round` 제거 가능 여부 확인(정수 입력이면 불요).

- [ ] R7 crit 배수: 정수 퍼센트(예 ×100 고정소수)로 표현해 부동 누적 제거 검토.
